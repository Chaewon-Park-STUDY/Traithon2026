# BK04. 통제 및 요구사항

작성일: 2026-10-02 | 팀명: 레드투그린

> 목적: BK02에서 식별한 위험 각각에 대해, 구체적인 **통제(Control)** 와 이를 보장하기 위한 **요구사항(Requirement)** 을 정의하고, BK03 아키텍처의 어느 부분에서 구현되는지 연결한다. (멘토링 3주차 가이드: 위험 → 통제 → 요구사항 → 아키텍처 연결 확인)

---

## 1. 위험별 통제·요구사항 매핑

| 위험 ID | 통제(Control) | 요구사항(Requirement) | 아키텍처 반영 위치 |
|---|---|---|---|
| RISK-01 (클릭베이트 미탐지 → 독자 피해) | 애매하면(conformal 예측집합이 두 클래스 포함·공집합) 자동 통과 대신 사람에게 이관 | 시스템은 모든 판단에 라벨 확률과 애매 여부를 함께 출력해야 한다 | BK03 아키텍처 "A.X 4.0 Light 판단" 단계 출력값에 확률·애매 여부 포함 |
| RISK-02 (정상 기사 오탐 → 신뢰·평판 피해) | 오탐 시 이의제기 채널 제공, 판정 근거 상시 공개 | 모든 "클릭베이트" 판정에는 근거(불일치 구간)가 함께 제공되어야 한다 | 검토자 큐 및 최종 게시 화면에 판정 근거 노출 |
| RISK-03 (검토자 경보 과부하 → 형식적 승인) | 우선순위 매트릭스로 검토 큐 정렬, 자동 승인 전환 금지 | 검토자 부재 시에도 큐는 쌓이기만 하고 자동 승인되지 않아야 한다 | BK03 "긴급도×중요도 매트릭스" + 운영 규칙 |
| RISK-04 (정치·경제 민감 주제 편향 판단) | 해당 카테고리는 매트릭스 계산 없이 즉시 인간 이관(자동판정 대상에서 원천 제외) | 정치·경제(특정 기업/종목) 카테고리 식별 로직은 판단 단계보다 먼저 동작해야 한다 | BK03 아키텍처 분기(전처리 직후 카테고리 분기) |
| RISK-05 (입력 이상 케이스 처리 실패) | 입력 전처리 단계에서 사전 필터링, 실패 시 "판단 보류" 반환 | 본문 누락·언어 혼재 등은 AI 판단 이전에 걸러져야 한다 | BK03 "전처리" 단계 |
| RISK-06 (탐지 기준 과잉 강화 → 정상 기사 과잉 차단 → 알 권리 침해) | 임계값을 중간값으로 설정 + 애매한 구간은 자동판정 금지, 인간 이관 | 시스템은 "클릭베이트 아님"으로도 "맞음"으로도 확신할 수 없는 애매 구간을 별도로 식별·표시해야 한다 | BK03 아키텍처 "A.X 4.0 Light 판단" 신뢰도 출력 + BK02 §6 트레이드오프 원칙 |
| 검토자 간 판단 불일치 (BK03 §4-3) | 경력 우선 적용 → 애매/민감 건은 전문가 재검토로 에스컬레이션 | 시스템은 동일 건에 대한 복수 검토자의 판단과 그 불일치 여부를 기록해야 한다 | BK03 §4-3, 기록 항목(4-1)에 포함 |
| RISK-07 (본문이 틀렸지만 제목과 일치하는 기사 통과) | ①의 판단 범위를 제목-본문 일치성으로 한정·고지, 사실 확인은 검토자 외부 출처 확인(또는 ② 검증 Agent 확장) | 시스템은 모든 판정 결과에 "사실 여부는 검증하지 않음" 고지를 함께 표시해야 한다 | BK01 §1(5), BK03 §4-1 제공 정보·사람의 행동 항목 |
| RISK-12 (② 외부 검색 근거 오염) | 출처 화이트리스트·링크 병기, 검색 결과 격리, 최종 사실 판단은 사람 | ②가 제시하는 모든 근거는 출처 링크와 함께 표시되어야 하며, 검색 결과는 지시로 해석되지 않아야 한다 | BK01 §1(3) ②, BK03 §5 |
| RISK-13 (변형 데이터로 인한 성능 과대평가) | Auto/Direct 분리 평가, 클릭베이트 보정은 Direct 표본 기준, 한계 고지, 본선 전 실제 기사 표본 점검 | 성능은 유형별로 분해해 보고하고 보장은 “이 데이터 분포에 한해”임을 명시해야 한다 | BaseKit 4 §4-4·4-5, BaseKit 5 §5-4, BaseKit 7 |
| RISK-08 (프롬프트 인젝션) | 본문을 데이터로 격리, 출력 형식 제약, 실행은 사람이 결정 | 모델 입력에서 기사 본문은 지시로 해석되지 않도록 구분되어야 하며, 형식을 벗어난 출력은 폐기되어야 한다 | BK03 §5 인젝션 통제 + A.X 출력 포맷 제약 |
| RISK-09 (회피 적응) | 검토 결과를 신규 패턴으로 환류, 주기적 재평가 | 검토자가 확정한 오탐·미탐 사례는 평가·보정용 데이터로 누적되어야 한다 | BK03 기록·피드백 단계 → BK07 모니터링 |
| RISK-10 (언어·도메인 편향) | 영어 보조 데이터는 보조 용도로 제한, 한국어 기준 평가, 언론사·주제별 성능 분해 | 평가 결과는 언어·주제별로 분해해 보고되어야 한다 | BK01 데이터 활용 기준, BK07 평가 계획 |
| RISK-11 (성능 저하) | 주기적 재평가, 임계값·보정 재조정 이력 기록 | 모델 버전과 임계값 변경 이력이 기록되어야 한다 | BK07 모니터링, 공통 요구사항(일관성) |
| 에이전트 환각 위험 (BK03 §5) | 판단 근거는 원문 인용 방식으로만 생성 | 자유 생성 근거(원문에 없는 문장)는 출력에 포함되어서는 안 된다 | A.X 4.0 Light 출력 포맷 제약(근거=원문 구간 인덱스) |
| 에이전트 과도한 자율권한 (BK03 §5) | 실행 행동(게시/반려)은 항상 사람이 결정 | Agent는 판단·분류까지만 수행하고 게시 여부를 자체 실행해서는 안 된다 | BK03 아키텍처 "검토자 큐" 이후 단계는 사람 전담 |

## 2. 공통 요구사항 (전체 시스템 수준)

- **애매 구간 판정(Conformal)**: 자동판정 여부는 고정 숫자 구간이 아니라, 한국어 보정 셋에서 도출한 q̂로 만든 예측집합이 {클릭베이트, 정상}을 모두 포함하거나 공집합인지로 결정하며, 이 경우 인간에게 이관한다. 보정 셋은 튜닝·테스트와 분리하고 분포 변화 시 갱신한다 (BK02 §7)
- **추적성**: 모든 판정·개입·결정은 타임스탬프와 함께 기록되어야 한다 (BK03 §4-1 "기록" 항목과 연결)
- **일관성**: 동일한 입력(제목+본문)에 대해서는 동일한 신뢰도 범위 내 판단을 반복 가능해야 한다 (모델 버전 고정 또는 버전 기록)
- **데이터 사용 원칙 준수**: 메인(AI-Hub)·보조(Webis) 데이터 외 데이터 추가 시 BK01에 명시한 설명(필요성·부족한 점·보완되는 신뢰성 문제) 기록 의무화

## 3. 요소 간 일관성 점검 (멘토링 6번 항목 자가 점검)

| 점검 항목 | 확인 |
|---|---|
| 문제 정의 ↔ 서비스 정의 | BK01 §0(문제 정의)의 "독자가 왜곡된 정보로 불필요한 판단을 내리지 않도록 게시 단계에서 미리 걸러준다"가 §1 서비스 정체성과 그대로 연결됨 ✅ |
| 서비스 개념·목적 ↔ 이해관계자 | BK01의 Onion Model(직접: 독자·검토자 / 간접: 작성자·대상기업·언론사·플랫폼운영사)이 서비스 정의와 직접 연결됨 ✅ |
| 이해관계자 ↔ 영향 | BK01 IMPACT-01~04가 각 이해관계자별 피해 경로 + 기본권 체크리스트로 설명됨 ✅ |
| 영향 ↔ 위험 | BK02 RISK-01~13가 각 IMPACT에 매핑됨(IMPACT-04 ↔ RISK-06, 일치성 한계 ↔ RISK-07, 에이전트·데이터 위험 ↔ RISK-08~11, 13) ✅ |
| 위험 ↔ 트레이드오프 | BK02 §6에서 RISK-01과 RISK-06이 하나의 임계값을 두고 상충함을 명시하고 책임 소재를 기록함 ✅ |
| 위험 ↔ 통제·요구사항 | 본 문서(BK04) §1에서 매핑 완료 ✅ |
| AI·모델 역할 ↔ 사람의 역할 | BK03 §5에서 Agent는 "판단·분류"까지, 사람은 "실행 결정"을 담당하도록 명확히 분리 ✅ |
| 통제·요구사항 ↔ 아키텍처 | 본 문서(BK04) §1 "아키텍처 반영 위치" 열에서 확인 ✅ |
