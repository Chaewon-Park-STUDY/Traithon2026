# BK02. 위험 식별 및 위험 등록부 (Risk Register)

작성일: 2026-09-30 | 팀명: 레드투그린

---

## 1. 위험 평가 기준 (가능성 × 영향 매트릭스)

| 구분 | 낮음(1) | 보통(2) | 높음(3) |
|---|---|---|---|
| **가능성** | 드물게 발생 | 주기적으로 발생 가능 | 빈번히 발생 |
| **영향** | 경미(개별 사용자 불편) | 중간(집단 신뢰 손상) | 심각(재산·평판·사회적 파급) |

위험 점수 = 가능성 × 영향 (1~9). **6점 이상은 우선 대응 대상.**

## 3. 잔여 위험 (Residual Risk)

경감 조치 적용 후에도 완전히 제거되지 않는 위험:

| 위험 ID | 잔여 위험 | 수용 여부 | 비고 |
|---|---|---|---|
| RISK-01 | 인간 이관 시에도 검토자가 판단을 그르칠 가능성 | 수용 | 검토자 교육·가이드라인으로 별도 보완 필요(BK03 이후) |
| RISK-04 | "민감 주제" 경계가 모호한 사례 존재 | 수용(모니터링) | 초기 민감 주제 키워드/카테고리 목록은 팀이 임의 정의 → 운영 중 지속 업데이트 필요 |
| RISK-07 | 본문이 틀렸지만 제목과 일치하는 기사는 ①이 구별할 수 없음 | 수용(범위 명시) | 사실 검증은 ② 검증 Agent 영역. 서비스가 "사실 여부를 보증하지 않는다"는 점을 사용자(검토자)에게 고지 |
| RISK-08 | 인젝션 기법이 계속 진화해 완전 차단은 어려움 | 수용(모니터링) | 입력 격리·출력 제약과 사람 결정 단계로 피해 확산을 제한하고, 검토자 신고 사례를 통제 개선에 반영 |
| RISK-10 | 영어 보조 데이터에서 얻은 기준이 한국어 기사에 그대로 맞지 않을 가능성 | 수용(검증 후 조정) | 보조 데이터는 인간 검토 기준 설정·비교용으로만 사용, 최종 평가는 한국어 데이터 기준 |
| RISK-13 | 변형으로 만든 공개 데이터로는 실제 기사 분포에서의 성능을 완전히 보장할 수 없음 | 수용(검증 후 조정) | 성능과 Conformal 보장은 “이 데이터 분포에 한해” 성립한다고 명시하고, 운영 데이터 누적 시 재보정 |

## 4. 대응 옵션 적용 원칙

1. **회피**: 애초에 자동 판단 대상에서 제외 (예: 민감 주제)
2. **경감**: 기술적·프로세스적 완화 조치 (RISK-01, 02, 03)
3. **이전**: 해당 프로젝트 범위에서는 미적용 (외부 위탁 없음)
4. **수용**: 잔여 위험으로 명시적 기록 후 진행 (RISK-05, 잔여 위험 표 참고)

> 수용은 "방치"가 아니라 **의식적 결정 + 기록**이어야 하므로, 위 표에 근거를 남긴다.

## 6. 트레이드오프와 책임 소재

> 멘토링 지적: 위험관리는 위험을 없애는 것이 아니라 **상충하는 위험 사이에서 선택하고, 그 선택에 책임지는 것**이다.

RISK-01(미탐지)과 RISK-06(과잉 차단)은 같은 손잡이(탐지 기준 임계값)의 양쪽 끝에 있다. 기준을 강화하면 RISK-01은 줄지만 RISK-06이 커지고, 완화하면 반대가 된다 — 즉 두 위험을 동시에 0으로 만들 수 없다.

| 항목 | 내용 |
|---|---|
| 팀의 선택 | **재현율(클릭베이트를 놓치지 않는 것)을 우선**하되(§7), 그 대가로 늘어나는 오탐·과잉 차단은 **판단이 애매한 경우(conformal 예측집합이 {클릭베이트, 정상}을 모두 포함하거나 공집합인 경우, §7)를 전부 사람에게 이관**하는 방식으로 제어한다. 임의의 숫자 구간을 쓰지 않고 데이터에서 도출하며, AI가 확신 없이 자동 판단을 내리는 경우 자체를 줄이는 구조 |
| 선택의 근거 | 자동판정의 오류(RISK-01, RISK-06) 모두 "독자 피해"로 이어지므로, AI 혼자 확신 없이 판정하게 두는 것이 가장 나쁜 결과라고 판단 |
| 책임 소재 | 임계값과 "애매함"의 범위를 최초로 정하는 주체는 AI기획자이며, 그 결정 근거를 본 문서(BK02)에 기록해 추적 가능하게 한다 |
| 재조정 절차 | 운영 데이터(오탐/미탐 사례)가 누적되면 팀 논의를 통해 임계값을 재조정하고, 변경 시점·근거·변경자를 기록한다 (BK04 공통요구사항 "일관성"과 연계) |

## 7. "정확하다"의 기준

> 멘토링 지적: "AI가 정확하게 판단했다"는 말 자체가 모호하다. 무엇을 기준으로 정확하다고 판단하는지, 그 기준은 누가 정하는지 명시해야 한다.

| 항목 | 내용 |
|---|---|
| 정확성의 정의 | 모델이 출력한 "클릭베이트 여부" 판단이 검토자(사람)의 최종 판단과 일치하는 정도로 정의한다 (정답은 사람의 최종 판단 — 모델 자체가 정답 기준이 될 수 없음) |
| 핵심 지표 | **재현율(Recall) 우선**: 클릭베이트를 놓치는 피해(RISK-01)가 정상 기사를 한 번 더 검토하게 되는 비용보다 크다고 판단. 보조 지표로 **정밀도 하한**을 두고 과잉 차단(RISK-06)을 모니터링 |
| 애매 구간 판정 (Conformal) | 한국어 보정 셋(AI-Hub 일부, 튜닝·테스트와 분리)에서 비적합도 s(x,y)=1−p̂(y∣x)의 분위수 q̂를 계산하고, 예측집합 C(x)={y : s(x,y)≤q̂}가 {클릭베이트, 정상}을 모두 포함하거나 공집합이면 "애매함"으로 보고 자동판정하지 않고 인간에게 이관한다 (§6 트레이드오프 적용 지점) |
| 보장과 허용 오류(α) | 클래스 조건부(Mondrian) conformal로 P(클릭베이트 ∈ C(x) ∣ 정답=클릭베이트) ≥ 1−α를 확보한다(= 확정 판정 또는 인간 이관에 포함). α는 "놓칠 확률 허용치"로, 재현율 우선(§6)과 오탐 증가(검토 부담) 사이의 팀 위험 허용도 파라미터이며 AI기획자가 정하고 근거를 기록한다 |
| 전제와 한계 | 보장은 교환가능성(보정 셋과 운영 데이터가 같은 분포)을 전제로 한 주변(marginal) 보장이며 개별 기사·하위집단별 보장은 아니다. 한국어 AI-Hub만 보정에 사용하고(영어 Webis는 분포가 달라 제외), 분포 변화(RISK-10·11)로 전제가 깨지면 보정 셋을 갱신한다 |
| 확률 품질 점검 | conformal의 비적합도에 쓰는 라벨 토큰 확률이 실제 정답률과 맞는지 점검(확률 구간별 정답률, ECE)하여 점수의 품질을 확인한다 |
| 임계값 설정 주체 | AI기획자가 초기값을 정하고, 팀 논의로 확정 — 즉 "정확하다"의 기준은 모델이 아니라 **팀이 운영적으로 정의한 합의값**임을 명시 |
| 판단 불일치 시 처리 | 검토자 간 최종 판단이 서로 다른 경우의 처리 절차는 BK03 §4-3("검토자 간 판단 불일치 처리")에서 별도로 정의 |

## 8. 역할 분담 (RACI)

> R=실행 / A=최종 책임 / C=협의 / I=공유. 아래는 3개 필수 역할 기준 초안이며, 실제 팀원 배정은 팀 확인 후 확정한다.

| 활동 | AI 기획자 | 데이터 과학자 | AI 엔지니어 | 검토자(운영팀) |
|---|---|---|---|---|
| 서비스 정의·이해관계자·영향 분석 | A/R | C | C | I |
| 위험 식별·등록부 관리 | A/R | C | C | C |
| 데이터 구성(메인/보조 활용·분할) | C | A/R | I | I |
| 신뢰도 보정·임계값(애매 구간) 설정 | A | R | C | I |
| 모델 호출·출력 형식·인젝션 방어 | C | C | A/R | I |
| 인간감독 절차·SLA 설계 | A/R | I | C | C |
| 민감 카테고리 목록 관리 | A/R | C | C | R |
| 검토 수행·판단 기록 | I | I | C | A/R |
| 잔여 위험 재검토·임계값 재조정 | A/R | R | C | C |
