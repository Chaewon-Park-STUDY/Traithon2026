# PREREG d36 — 중단·재개 재생 시연 (stop / resume replay)
작성일 2026-11-10. 실행 전에 커밋한다.

## 질문
용량 초과 대응 규칙(BaseKit Part B 5-B6)이 단계별로 작동하고, 중단 후 운영 책임자 승인으로 재개되는 흐름이 로그와 테스트 표로 재현되는가.
평가 연결: A7 Human Oversight(개입·중단·복구), BK-06 §4.8(중단·safe state·재개), §4.9(테스트 표).

## 성격 (반드시 명시)
- 모의 재생(simulated replay)이다. 실제 운영 데이터가 아니다.
- 시나리오 입력(접수량, 검토자 수)은 시연영상 장면의 값(1,000건/3명, 750건/2명, 1,000건/2명)을 그대로 쓴다. 새 숫자를 만들지 않는다.
- 상수는 demo_app.py와 같다: 검토자 1명 하루 150건(가정 A4), 기사 1건당 검토 부하 0.376(실측, 유병률 10% 가정).

## 규칙 출처
- 5-B6 문구: 90% 초과 알림, 100% 초과 확인 큐 게시 보류(자동 통과 확대 금지), 3일 연속 초과 또는 24시간 넘은 대기 건이면 신규 기사 자동 처리 중지.
- 코드 구현(demo_app.py)과 일치 여부는 스크립트의 drift check로 확인한다.
- 시연_안내.md의 "30시간"은 오기. 24시간이 맞다(5-B6 원문, 코드 max_wait >= 24).

## 팀이 새로 정하는 규칙 (5-B6에 없음, 제안)
- 재개 조건 R: (a) 운영 책임자 승인이 기록되고, (b) 증원 등 조정 후 사용률이 90% 이하이고, (c) 24시간 넘은 대기 건이 없을 것. 하나라도 어긋나면 중지 상태 유지.
- 중지 상태에서는 승인 없이 단계가 내려가지 않는다(latch).
- 이 규칙은 설계 결정이며, BK-06 §4.8에 근거와 함께 적는다.
- BK-06 §4.8 재개 행의 열과 대응: 계획된 조건 = 원인 확인(대기 원인 기록), 수정(검토자 증원 등 조정), 재시험(조정 후 사용률 90% 이하·24시간 넘은 대기 없음) / 재개 범위 = 전체 서비스(단계적 재개는 팀 결정 후 추가) / 승인 역할 = 운영 책임자 / 승인 근거 = 로그의 승인 기록.
- BK-06 §4.8 안내에 따라 중단 조건은 §4.5 즉시 중단 기준 ID와 일치시켜야 한다. 이 스크립트의 중단 조건(3일 연속 초과, 24시간 대기)에 §4.5 ID를 부여하는 일은 문서 작성 단계에서 한다.
- BK-06 §7 구현 상태 표의 구분(구현 / 시뮬레이션 / 제외)에서 이 재생은 시뮬레이션으로 표기한다.
- 위 열 대응은 BaseKit v1.1 BK-06 §4.8, §4.9 표 구조 기준이며, 증빙 ID(EVD)는 팀의 번호 체계에 맞게 부여한다.

## 경계 해석
- "넘으면"은 초과(>)로 해석: 사용률 정확히 100%는 게시 보류가 아님, 정확히 90%는 경고가 아님이 5-B6 문구 그대로의 읽기다. 코드가 >=0.9이면 코드 기준을 따르고 차이를 보고한다(drift check가 출력).
- 대기 24시간은 이상(>=24)으로 코드와 맞춘다.
